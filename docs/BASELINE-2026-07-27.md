# The baseline — first honest measurement of the deployed app

**Pass 2, Phase 2.** Measured against `https://finalevolution.abacusai.app` on
2026-07-27 with `node tools/integration_audit.mjs`. Raw data in
`artifacts/integration-audit.json`; screenshots in
`docs/abacus-batches/m95-pass2-canvas-and-baseline/evidence/`.

This is the first time in ninety-five batches that anything in this project has
been **measured in the product** rather than tested in the repo.

## 2. Boot — better than assumed

| | |
|---|---|
| DOM ready | 1.2 s |
| canvas present | **1.2–2.5 s** (cold 2.5 s, warm 1.2 s) |
| reaches `playing` | every one of eight modes |

`boot` moves from **UNKNOWN to measured**. It is not a problem. This has been
on the worry list since M74 and it should come off — on a data-centre network
against a warm CDN, which is a floor and not the number a player on 4G sees.

**Every mode reached `loading → loaded → playing`.** There is no "you must
refresh the page to load a game" reproduction in eight modes at two viewports.
Whatever that symptom is, it is not a mode failing to boot.

## 3. Canvas — the finding

| viewport | coverage | verdict |
|---|--:|---|
| desktop 1280×720 | 92.1% | fine |
| **iPhone 13 390×844** | **26–33%** | **the bug** |

Identical on `dunk`, `onevone`, `karate`, `skateboard`, `tennis`, `surf`,
`football`, `baseball` — to the decimal. **It is one shared wrapper, not
twenty-five mode bugs:**

```html
<div class="relative aspect-[16/10] w-full overflow-hidden rounded-xl ...">
```

A 16:10 box across a 390px portrait phone is 244px tall. The canvas inside it
is `absolute inset-0` and was never the problem — which is why every
`engine.resize()` theory failed. The bottom third of the phone screen is empty
black.

**Fixed and verified: 33.3% → 79.8% on eight modes, no control pushed
off-screen.** See M95.

### The second half of it

| | |
|---|---|
| canvas CSS box | 372 × 232 |
| backing buffer | 1116 × 696 |
| **backing pixels per CSS pixel** | **9.01** |

`devicePixelRatio` 3 taken literally. The phone fills 776,736 pixels to light
up 86,304, and the extra eight are invisible at that size. Capping at 2 removes
**56% of the fill rate** for no perceptible change. Fill rate is the dominant
cost on a mobile GPU, so this is the single largest framerate item found so
far — and nobody had looked.

## 4. The T-pose is still there

**This corrects something I said earlier in this project.** I reported that
M64 had fixed the T-pose, on the strength of the console line:

```
[FEL-ANIM] restPose solved for 4 bone(s): LeftArm, RightArm, LeftForeArm, RightForeArm
[FEL-ANIM] restPose applied to skeleton for 4 bone(s): LeftArm_c21, ...
```

It runs. **The characters are still T-posed** — both of them, on desktop and
phone, arms straight out. See `evidence/desktop-tpose.png`.

A console line saying a fix ran is not evidence the fix worked, and I treated
it as one. The likely mechanic: `restPose` corrects the *skeleton's rest pose*,
and then a playing clip with arm rotation keys overrides it every frame. The
importer log supports that — it drops **position** tracks (`dropped 52 position
track(s)` on each of nine clips) and leaves rotations, which is correct
behaviour and leaves exactly this hole.

Not fixed here, because confirming it needs `PoseProbe` (M80, built, not
wired) or the app source. **It is the top per-mode blocker and it is visible in
every screenshot of the product.**

## 5. No WebGL leak — and the reason matters

Six route changes, instrumented at `HTMLCanvasElement.getContext` before any
app code ran:

```
route        ctxCreated  ctxLost  canvases
dunk                  1        0         1
onevone               1        0         1
skateboard            1        0         1
karate                1        0         1
```

One context per route, every time. **Every route change is a full page load** —
there are no in-app `/play/` links, so the browser tears the context down
itself and there is nothing to leak.

M81's engine-lifecycle work is written against a leak this build's routing
already prevents. That does not make it wrong: the moment the app becomes a
true SPA, or React StrictMode double-mounts in dev, the leak is real. But
**"the WebGL context leak" should stop being cited as a live defect**, and I
have cited it as one for several batches.

## 6. What this changes about the plan

| criterion | was | now |
|---|---|---|
| boot | UNKNOWN | **measured — not a problem** |
| canvas | SPECIFIED | **measured FAIL, root-caused, fixed in M95** |
| lifecycle | BUILT | **the defect it targets is not reproducible in this build** |
| no_tpose | BUILT | **measured FAIL — visible in the product** |
| framerate | UNKNOWN | one large item found (9× fill); still unmeasured on real hardware |

Two criteria leave UNKNOWN. One leaves BUILT for FAIL, which is worse news and
better information.

### What still cannot be measured from here

- **Framerate.** This container renders through SwiftShader; the 3fps it
  reports is the software rasteriser, not the product. Only real hardware
  answers this.
- **Anything below the bundle.** `window.BABYLON` is not exposed, so the scene
  graph, the animation groups and the bone rotations cannot be inspected from
  outside. `PoseProbe` exists to report from inside and is not wired.
- **Fun.** Still only the founder can score it.

The product boots fast, loads every mode, has no context leak, gives the game a
third of a phone screen, renders nine pixels per visible pixel, and shows every
character in a T-pose.
